FHIR essentials · Lesson 1

FHIR basics

Resources, the REST API, references, versions, requests and responses: the ground every other lesson stands on.

Resource: one record

A typed JSON (or XML) document with its own id and version history: Patient, Observation, Appointment. This tutorial uses R4 (4.0.1), the version CH Core builds on.

Bundle: many records in one

A resource that carries other resources: a page of search results, a set of writes to run together, a document (see Bundles).

1A resource

  • resourceType names the type; id is the server's handle for it (see Identifiers).
  • meta holds versionId, lastUpdated and profile claims (see Profiles).
  • Everything else is the type's own elements, mostly optional, each documented on that type's page in the spec.
{ "resourceType": "Patient",
  "id": "123",
  "meta": { "versionId": "3",
    "lastUpdated": "2026-11-01T09:30:00+01:00" },
  "name": [ { "family": "Muster",
              "given": [ "Franz" ] } ],
  "birthDate": "1995-01-27" }

2The REST API

readGET Patient/123
vreadGET Patient/123/_history/3: one old version
createPOST Patient: the server picks the id
updatePUT Patient/123; a new id creates it, if allowed
deleteDELETE Patient/123
searchGET Patient?family=Muster
historyGET Patient/123/_history
capabilitiesGET metadata: what this server supports
transaction, batchPOST a Bundle to the base URL

3References

  • "reference": "Patient/123" is relative to the server's base; an absolute URL points elsewhere.
  • A logical reference holds an identifier instead; servers may accept, resolve or reject it.
  • One-way: an Observation points at its Patient, but the Patient doesn't list its Observations. Walk back by searching: Observation?subject=Patient/123.
  • Whether a write with a missing target is refused depends on the server (HAPI can enforce it).

4Versions

  • Every update bumps meta.versionId; old versions stay readable (vread, history).
  • Lost updates: send If-Match: W/"3" with the PUT. If someone saved version 4 in the meantime, the server answers 412 Precondition Failed instead of overwriting.
  • Conditional create: If-None-Exist: identifier=... creates only when nothing matches; one match returns 200 and creates nothing; several return 412.

5Requests and responses

Content-Typeapplication/fhir+json, also in Accept
Preferreturn=representation sends the stored resource back
Location[base]/Patient/124/_history/1 after a create
ETagW/"3": send it back in If-Match
200, 201Updated; created
400Can't be parsed, or fails basic FHIR rules
404Not found, or not a FHIR endpoint
405PUT to a new id; the server assigns ids itself
409, 412Version conflict (see Versions)
422Breaks a profile or a business rule; an OperationOutcome says which

×When it breaks

  • 406 or 415: the server can't send the format asked for in Accept (406), or can't read the body's Content-Type (415). Use application/fhir+json in both.
  • 400 on a PUT: the body has no id, or one that differs from the id in the URL.
  • 201, but another id: a create ignores any id in the body; take the new one from Location.
  • 201 with no body: without a Prefer header the server decides whether to send the resource back; ask for return=representation.
  • 410 on a read: the resource was deleted; 404 means it never existed, or the server doesn't track deletes.
  • 200 and an empty Bundle: a search that matches nothing still succeeds; it never answers 404 for no hits.

!Rules of thumb

  • Read GET metadata first: it says what this server actually supports.
  • Update with If-Match; without it the last writer silently wins.
  • On an error, read the OperationOutcome in the body before guessing: it names what failed.

FHIR essentials · Lesson 2

Data types: what the JSON really says

The types every element is built from, the JSON rules parsers get wrong, choice elements, and resources inside resources.

Primitive types: one value

boolean, integer, decimal, string, code, date, dateTime and more.

Complex types: reusable structures

Quantity, Period, CodeableConcept, Identifier, Reference: the same wherever used.

1Primitives in JSON

integer, decimalJSON number: "value": 72.50
booleanJSON true or false, never "true"
everything elseJSON string, dates and codes included: "birthDate": "1995-01-27"

integer is 32-bit; id is 1 to 64 of A-Z a-z 0-9 - .; a string is at most 1 MB.

  • No value, no property: "properties never have null values": no null, "", {} or [].
  • Arrays even for one item, in order; property order is free.
  • Choice elements: [x] becomes the type (valueQuantity, effectivePeriod), one per instance. Observation allows eleven value[x] types: read only valueQuantity and you miss the rest.

2Decimals keep their precision

  • R4: "0.010 is regarded as different to 0.01". Float parsers drop the zeros (in JavaScript "2.00 will be converted to 2"): parse into a decimal type.
  • Quantity: unit for people, system plus code for software, UCUM where the unit exists there.
  • comparator is a modifier: "<" makes 0.5 "less than 0.5". Code that reads only value gets it wrong.
"valueQuantity": {
  "value": 0.5,
  "comparator": "<",
  "unit": "mg/L",
  "system": "http://unitsofmeasure.org",
  "code": "mg/L" }

A CRP below the detection limit. Values made up.

3Dates, times and time zones

date1974, 1974-06, 1974-06-15: "There SHALL be no time zone"
dateTimeThe same, or 2026-11-01T08:15:00+01:00: with a time, "a time zone SHALL be populated"; seconds required
instantTo the second, always with a zone: meta.lastUpdated

Period: both ends inclusive; no end means "no end was known or planned".

  • Date.parse("1995-01-27") reads a date-only string as UTC, "1995-01-27T00:00:00" as local time: a birthDate turned into a timestamp can end up a day off.
  • "1974" is a valid birthDate; padding it to 1974-01-01 invents precision.
  • Swiss offsets: +01:00 in winter, +02:00 in summer. Read it, never assume it.

4Contained resources

  • Inline in contained, referenced as "#med1". It "does not have an independent existence": no URL, search or update of its own.
  • Never nested; no meta.versionId or lastUpdated; it must reference its container or be referenced from it.
  • R4: "This SHOULD NOT be done when the content can be identified properly".
{ "resourceType": "MedicationRequest",
  "contained": [ {
    "resourceType": "Medication", "id": "med1",
    "code": { "text": "Salbe nach Rezeptur" } } ],
  "status": "active", "intent": "order",
  "medicationReference": { "reference": "#med1" },
  "subject": { "reference": "Patient/123" } }

A compounded ointment: no product, nothing to identify. Values made up.

×When it breaks

  • Your parser rejects null: FHIR JSON uses it in one place. A repeating primitive with extensions comes as two arrays, given and _given, padded with null so the positions line up.
  • _birthDate but no birthDate: a primitive can carry an extension and no value; then only the _ property is sent. Map the _ properties too, or a read-modify-write drops them.
  • 400 for a property you sent, or success and it's gone: a receiver may ignore unknown properties, or may refuse them. A misspelt name or an R5 element lands here (see FHIR versions): read the stored resource back.
  • A Quantity fails qty-3: it has a unit code but no system. For UCUM units, send http://unitsofmeasure.org with it.

!Rules of thumb

  • Parse decimals without loss; keep date and dateTime as strings or date-only types.
  • Leave a property out instead of sending null, "" or [].
  • Handle every [x] variant you accept, and reject the others explicitly.
  • Contain only what has no identity of its own: anything with an identifier gets its own resource and a Reference.

FHIR essentials · Lesson 3

Identifiers in Swiss FHIR

Why a resource carries several identifiers, why their systems look like urn:oid:2.51.1.3, and what a GLN is.

id: the server's handle

The 123 in Practitioner/123. Means something on that server only: a reload, a migration or another environment (dev, stg, prod) can give the same person another one.

identifier: the business key

A system (a URI naming the namespace) plus a value. Survives copies, reloads and environments, and you find the resource by it.

1One thing, many numbers

The same person is known to several systems, each with its own number. FHIR doesn't pick a winner: it lists them all, and each one names its system, so every consumer picks the one it knows.

A USB patientSAP patient number, AHV number (AHVN13), EPD patient ID (EPR-SPID), insurance card number, an openEHR EHR ID
A physicianGLN, ZSR number (billing), SAP personnel number, Entra ID account
system + valueWhere the number comes from, and the number. These two are what matters.
useusual, official, temp, secondary, old (for example after a merge)
typeWhat kind of number it is
period, assignerWhen it was valid, who issued it
"identifier": [
  { "system": "urn:oid:2.51.1.3",
    "value": "7601000000019" },
  { "system":
      "https://example.usb.ch/sid/staff-nr",
    "value": "123456" }
]

Illustrative: the second system URI and both values are made up.

2Why urn:oid: looks so weird

system must be a URI. A new namespace can simply be a URL, but many health namespaces are older and use an OID (Object Identifier): an ISO/ITU numbering tree dating from the 1980s. Each number is a branch; an organisation gets one and hands out sub-branches. urn:oid: just wraps the number so it counts as a URI.

2.16.756Switzerland (2 ISO/ITU root, 16 countries, 756 its ISO code)
2.16.756.5.32AHV number (AHVN13), e.g. 7561234567897
2.16.756.5.30eHealth-CH, the Swiss health branch, run by RefData (oid.refdata.ch)
2.51.1.3GLN, in GS1's branch (2.51)

Never meant for humans: globally unique, no DNS, stable for decades. HL7 v2, CDA and the EPD's IHE profiles use them, so CH Core kept them.

3GLN: Global Location Number

  • A 13-digit GS1 number. Swiss health professionals' GLNs start with 7601; the last digit is a check digit.
  • RefData assigns them to health professionals and organisations. Anyone in a profession on RefData's list of health professions can get one.
  • Medical professionals' GLNs are listed in MedReg (BAG), which is public: a GLN is not a secret.
  • Used for invoices, prescriptions and the EPD identity of a health professional. CH Core has an identifier profile for it (ch-core-gln-identifier).
  • The catch: only registered health professionals have one. A minute-keeper or a secretary usually doesn't, so the GLN alone can't key every staff member.

×When it breaks

  • 200 and an empty Bundle, but the record exists: token search compares the system literally. 2.51.1.3 without urn:oid:, http for https or a trailing slash finds nothing: copy the system exactly.
  • 200 and empty for an AHV number: it was sent with dots, 756.1234.5678.97. CH Core wants exactly 13 digits and no dots. Strip dots and spaces before you store or search; GLNs too.
  • Found by the bare value, but not by system|value: the stored identifier has no system; identifier=|value finds exactly those. Fix the data: a number without its system could be anyone's.

!Rules of thumb

  • Never key a mapping, or a link between systems, on a server id. Use an identifier: ids differ per environment and can change on a reload.
  • Always search with system and value: Practitioner?identifier=urn:oid:2.51.1.3|7601000000019. A value on its own matches any system.
  • For staff: the GLN where there is one, a local number (such as the personnel number) for everyone else.
  • Before designing a model, fetch a few real resources from the server and look at which identifier systems they actually carry.

FHIR essentials · Lesson 4

Terminology: codes, systems and value sets

The three shapes a code takes, how strictly a profile can bind it, what a terminology server does, and the Swiss side.

CodeSystem: the dictionary

Defines codes and what they mean, under a canonical URL: SNOMED CT is http://snomed.info/sct, LOINC http://loinc.org. The big ones live on a terminology server.

ValueSet: the allowed list

Picks the codes allowed for one use, from one or more CodeSystems, by listing them or by a rule (say, every descendant of a SNOMED concept). Profiles bind elements to ValueSets, never to CodeSystems.

1Three shapes of a code

codeJust the code; the element's definition fixes the system. Used for FHIR's own lists, such as status or gender.
Codingsystem and code, plus display and version: one code from one system.
CodeableConceptOne or more Codings for the same meaning, plus text: what the user saw or typed.
"code": {
  "coding": [
    { "system": "http://snomed.info/sct",
      "code": "44054006",
      "display": "Type 2 diabetes mellitus" },
    { "system":
        "https://example.org/cs/diagnoses",
      "code": "DM2" }
  ],
  "text": "Diabetes Typ 2, diätetisch eingestellt"
}

SNOMED CT code checked with $lookup on tx.fhir.org; the local code and the text are made up.

2Binding strengths

requiredThe code SHALL come from the ValueSet; text alone doesn't count.
extensibleFrom the ValueSet if any code there fits; if none does, another code (or text) is allowed.
preferredEncouraged for interoperability, not needed to conform.
exampleOnly shows the kind of codes meant.

3The terminology server

$lookupDetails of one code: display, properties, other names
$validate-codeIs this code in this ValueSet? true or false
$expandThe current codes of a ValueSet, optionally filtered by text
$subsumesIs one code a kind of another? 73211009 Diabetes mellitus subsumes 44054006
$translateMap a code to another system, using a ConceptMap

4The Swiss side

  • SNOMED CT: Switzerland has been a member of SNOMED International since January 2016. The FOPH gave the National Release Centre to eHealth Suisse, which issues the licences (through SNOMED International's MLDS portal); use in Switzerland is free. eHealth Suisse translates into German and French with other release centres, into Italian on its own, and a Switzerland extension comes out twice a year.
  • CH Term (ch.fhir.ig.ch-term#3.4.0): "terminology that is used in Switzerland for the core profiles": EPD metadata from the annexes of the EPD ordinance, BFS statistics, eCH, vaccination, plus imported systems such as SNOMED CT, EDQM and UCUM.

×When it breaks

  • 200, but result is false: $validate-code answers in a Parameters body, so read result and message, not the status. A wrong display can fail it: send the system's display, or none.
  • too-costly from $expand: the value set has too many codes to expand whole. Add a text filter, or page with offset and count where the server supports paging.
  • Your app refuses a code that's valid now: it checks a cached expansion, which R4 calls "a transient result that will change over time". Expand again when you use it, or ask $validate-code.
  • result false for a Swiss SNOMED CT code: without a version the server uses its default edition, often the International one. For Swiss extension codes, send version http://snomed.info/sct/2011000195101.
  • No match for a code you know: the system is written another way, such as SNOMED CT's OID. Where R4 defines a URI it "SHALL be used": http://snomed.info/sct, http://loinc.org.

!Rules of thumb

  • Always send system with a code: a code without its system means nothing.
  • display is a label for people; software compares system and code only.
  • Keep what the user saw in CodeableConcept.text: it survives when no code fits.
  • Your own codes need your own CodeSystem and ValueSet, under canonical URLs you own (see Extensions), never bare strings.
  • Ask the terminology server ($validate-code, $subsumes) instead of hard-coding code lists and hierarchies.

FHIR essentials · Lesson 5

Bundles: many resources, one request

How to send several writes at once, make them safe to send twice, read what comes back, and page through search results.

transaction: all or nothing

The server "SHALL either accept all actions" or reject them all; a failure returns a single OperationOutcome and stores nothing. Entries may depend on each other.

batch: each entry on its own

"There SHALL be no interdependencies" between the entries. The response is 200 even when entries fail: check each entry's status.

1Anatomy of a transaction

POST [base]
{ "resourceType": "Bundle", "type": "transaction",
  "entry": [
    { "fullUrl": "urn:uuid:3f6c2a9e-8d41-4b7a-a5e2-1c9d0b7e4f21",
      "resource": { "resourceType": "Patient",
                    "identifier": [ { "system": "https://example.org/sid/patient-nr", "value": "100234" } ] },
      "request": { "method": "POST", "url": "Patient",
                   "ifNoneExist": "identifier=https://example.org/sid/patient-nr|100234" } },
    { "fullUrl": "urn:uuid:9b2e7d14-0c3f-4e86-b1a7-5d8e2f6c3a90",
      "resource": { "resourceType": "Observation", "status": "final", "code": { ... },
                    "subject": { "reference": "urn:uuid:3f6c2a9e-8d41-4b7a-a5e2-1c9d0b7e4f21" } },
      "request": { "method": "POST", "url": "Observation" } }
  ] }
  • fullUrl names the entry; a new resource gets a urn:uuid: and others point at it by that urn. On a POST the server assigns a real id and "SHALL also update any references to that resource in the same bundle".
  • request says what to do: method, url, and optional conditions such as ifNoneExist or ifMatch.

Sent twice, this makes no second Patient but a second Observation: that entry needs a condition too (section 4). Values made up.

2Processing order

Whatever the order in the file, the server runs DELETE, then POST, then PUT and PATCH, then GET and HEAD, and resolves conditional references last. Two writes to the same resource make the transaction fail.

3Responses

  • Success: a transaction-response or batch-response, one entry per request in the same order, with status, location, etag.
  • Failed transaction: one OperationOutcome, no Bundle.
  • Batch: check every response.status.

4Conditional operations: safe to send twice

Conditional create"ifNoneExist": "identifier=system|value": no match creates; one match does nothing; several give 412.
Conditional updatePUT Patient?identifier=system|value: no match creates; one match is updated; several give 412.
Conditional reference"reference": "Patient?identifier=system|value", in transactions only: the server puts in the one match; none or several, and the transaction fails.

5Search results: searchset

  • total counts all matches, "not how many resources are returned" on this page.
  • The paging links (next and friends) "are opaque to the client": "The client must use the server supplied links".
  • entry.search.mode: match for results, include for what _include or _revinclude pulled in, outcome for an OperationOutcome with warnings.
  • Two types carry a whole unit rather than requests: a document starts with a Composition, a message with a MessageHeader.

×When it breaks

  • 201, but no entry was processed: the Bundle went to [base]/Bundle, which stores it as one resource, as is. POST transactions and batches to [base] itself.
  • A batch entry fails, or keeps its urn:uuid: reference: the entries of a batch can't point at each other; R4 calls that non-conformant. When one entry needs another, use a transaction.
  • 200, but other ids than you sent: a server may assign new ids to every resource in a batch or transaction, whatever id or fullUrl you gave. Take each id from response.location.
  • A short page, or no total: a server may return fewer entries than _count, and total stays optional even with _total=accurate. Page until there's no next link.
  • The same resource on two pages: included resources come again on each page that needs them, and data that changes while you page can move matches between pages. De-duplicate by fullUrl.

!Rules of thumb

  • Give new resources urn:uuid: fullUrls and reference them by that urn; never guess ids.
  • Key every write on an identifier (conditional create, update, reference): then a retry after a timeout does no harm.
  • A transaction when entries depend on each other; a batch when they don't, and then check each entry.
  • Page with the server's next link; never build page URLs yourself.

FHIR essentials · Lesson 6

Search: asking the server the right question

How each parameter type matches, modifiers, chains and includes, and parameters the server doesn't know.

GET [type]?name=value: always a Bundle

A searchset with 200 OK, even with no matches: "An empty search result is not a failure." Parameter names are case sensitive.

Unknown parameters are dropped

R4: "servers SHOULD ignore unknown or unsupported parameters": a typo returns everything. The self link shows what was applied.

1Parameter types

stringPatient?family=muller: "case-insensitive and accent-insensitive", equals or starts with, so it finds Müller and Müller-Huber. :exact matches case and accents, :contains anywhere.
tokencode=http://loinc.org|2823-3; system| any code in that system; a code alone matches any system.
datebirthdate=1974 matches any day in 1974: values are ranges, set by their precision.
number, quantityvalue-quantity=5.4 means "5.4(+/-0.05) irrespective of the unit"; add |http://unitsofmeasure.org|mmol/L for the unit.
referencesubject=Patient/123; patient is the same, limited to Patient targets.
othersuri: ValueSet?url=...; composite: two values joined by $; special: near on Location.

2Prefixes, AND, OR

  • Dates, numbers and quantities take a prefix: eq (the default), ne, gt, lt, ge, le, sa, eb, ap.
  • AND: repeat the parameter, as for a date range. OR: a comma, language=FR,NL. A literal comma, $ or | needs a backslash, on top of the URL's percent-encoding.
GET [base]/Observation?patient=Patient/123
    &code=http://loinc.org|2823-3
    &date=ge2026-01-01&date=lt2026-04-01
    &_sort=-date&_count=50

Potassium results in the first quarter of 2026, newest first; LOINC 2823-3 is "Potassium [Moles/volume] in Serum or Plasma". Values made up.

3Modifiers

:missing=trueNo value at all; with a value for the same parameter "always return[s] an empty list"
:notAlso returns resources with no value
:textSearches text and display, not codes
:below, :inSubsumption and ValueSets, via terminology
:identifiersubject:identifier=system|value: by the target's identifier; no chaining

An unsupported modifier SHALL be rejected: 400 with an OperationOutcome.

4Chains and includes

  • Chain into the target: Encounter?practitioner.identifier= and a GLN. Name a type if there are several: subject:Patient.name=peter. Two chains are independent: no one target has to match both.
  • Reverse: Patient?_has:Observation:patient:code=...
  • _include=Encounter:service-provider adds targets, _revinclude=Provenance:target what points in; repeat it, no commas; :iterate goes further. Missing targets are skipped silently.

5Results and errors

_countMost per page; 0: only total
_sort-date sorts descending
_elementsFewer elements, tagged SUBSETTED: never store them back
  • Bad syntax: 400. Refused: 403. Unknown resource type: 404. An unknown code or patient is no error: 200, empty.
  • POST [type]/_search with a form body means the same as GET and keeps patient data out of URLs, which R4 warns end up in logs.

×When it breaks

  • 400 on subject=123, or hits of another type: subject can point at a Patient, a Group and more, and servers only SHOULD reject an id that exists in several types. Write subject=Patient/123.
  • 415 on POST _search: the body must be form data, application/x-www-form-urlencoded, not JSON. A parameter in both the URL and the body counts as repeated.
  • One Encounter matches both gt and lt: prefixes compare ranges, so a period or a date-only value that spans your boundary matches either side. sa (starts after) and eb (ends before) leave it out.
  • _sort=-date&_count=1 returns an old one: servers only SHOULD honour _sort. The self link shows the sort the server really applied.
  • Hits missing or extra at the edges of a time range: without a time zone, the server picks one, often its local time. Send Z, or the offset with + encoded as %2B.

!Rules of thumb

  • Check the self link, or send Prefer: handling=strict: a misspelt parameter silently widens the result.
  • Search tokens with system|code; a bare code matches any system.
  • Read GET metadata for the parameters, modifiers and includes this server supports; chaining and includes are optional.
  • Search with patient data by POST _search, not in the URL.

Operations and PATCH

What the plain REST verbs can't say: named operations with a $, and changing part of a resource without sending all of it.

Operation: $name

A named function on the whole server ([base]/$meta), a type (Patient/$match) or one resource (Patient/123/$everything). Defined by an OperationDefinition; GET metadata lists the ones a server offers.

PATCH: change part of a resource

JSON Patch, XML Patch or FHIRPath Patch. Once applied, the server "processes the resulting document as an Update operation": versions, profiles and errors as for a PUT.

1Calling an operation

  • POST a Parameters resource with the "in" parameters; the answer is a Parameters resource with the "out" ones.
  • GET works when every parameter is primitive and the operation doesn't change state; "Servers SHALL support" it then: GET [base]/ValueSet/$expand?url=...&filter=abdo.
  • Exactly one resource as input: it may be the bare body. A single resource output named return comes back bare, without Parameters: $validate answers with an OperationOutcome, $everything with a Bundle.
  • No parameters but a change of state: POST with an empty body ("a parameters resource cannot be empty").
  • Success is 2xx (or 303); 4xx or 5xx carry an OperationOutcome.

6PUT replaces, PATCH edits

  • A PUT "updates the whole content of the resource": whatever you leave out is gone. The server can't tell what you dropped because you don't support it from what you meant to delete.
  • So a PUT is read, modify, write back with If-Match, and handle a 409 or 412.
  • PATCH names only what changes: R4 suggests it for low bandwidth, or when a client "has only partial access or support for a resource".
  • Retries: the same PUT twice gives the same result; a retried append adds a second email. With If-Match the retry gets a 412 instead.

×When it breaks

  • An error on add to /telecom/-: JSON Patch needs the array to exist, and a Patient without phone or email has no telecom at all. Add /telecom as a one-item array instead; on an existing array, that replaces it.
  • A FHIRPath Patch add fails on a single element: add works on non-repeating elements only while they don't exist yet. Use replace then; it fails the other way round, when the element is absent.
  • No value[x] fits Patient.contact or Observation.component: they have no data type of their own. Give the value part nested parts instead, one per child element.
  • PATCH refused, or text changed by it: the server must keep the narrative safe. It may reject a PATCH when text.status isn't generated, or regenerate or delete the narrative.
  • A 3xx other than 303 from an operation: the operation didn't run, often because of a redirect to log in. Handle the redirect, then send the operation again.

!Rules of thumb

  • Check GET metadata for the operations and the PATCH support of this server; both are optional.
  • $validate answers 200 for invalid resources too: read the issues, not the status code.
  • Send every PATCH and PUT with If-Match: it turns a lost update or a doubled append into a 412.
  • Prefer FHIRPath Patch when you select elements by content, and in Bundles, where it's the only format.
  • Never PUT a partial resource: read it fresh, change it, write it back.

Change feeds: keeping a copy in sync

Four ways to find out what changed on a server since you last asked, and what each one misses: deletes, the versions in between, the event that never arrived.

Pull the history: _history?_since=

Every create, update and delete since your checkpoint, deletes included, as a Bundle of type history. The spec's own way to keep two systems in sync.

Search by _lastUpdated misses deletes

A deleted resource is "no longer found through search", and three updates since your last poll show up as one. Good for "what's new", wrong for a mirror.

  • Read 410 as deleted and 404 as unknown: only a 410 or a DELETE entry tells your copy to go.

FHIRPath: the language inside the rules

The small path language behind invariants, search parameters, slicing and FHIRPath Patch. Its one big idea: every result is a collection, and missing data is an empty one, not null and not an error.

Everything is a collection

Patient.name.given returns every given name of every name, in order, duplicates kept. An element that isn't there gives { }, the empty collection.

= on a list is not "contains"

7When it errors, and when it quietly says no

  • Errors: two items where one is expected. name.family + ', ' + name.given.first() with two names; name.single(); identifier.value.startsWith('760') with two identifiers, since string functions take one string; < and > on lists.
  • Narrow first: identifier.value.where($this.startsWith('760')), or require count() = 1.
  • fhirpath.js doesn't set %resource by itself; pass it in, or the rule fails with "undefined environment variable".
  • Quietly wrong: = with a list on one side gives false. One passage of the spec says error here; its rules and fhirpath.js say false.
  • children(), descendants(), repeat(), distinct() and | promise no order: no first() after them.
  • @2018-03 > @2018-03-01 gives { }; how a dateTime without a time zone compares is "a policy decision".
  • Strings order by Unicode value: 'abc' > 'ABC' is true.

  • fhirpath.js (HL7, JavaScript) returns an array. resolve() and memberOf() need { async: true } plus fhirServerUrl or terminologyUrl. On the command line: fhirpath --expression 'Patient.name.given' --resourceFile pt.json.
  • FHIRPath Lab (fhirpath-lab.com) runs one expression on several engines: Firely (.NET), HAPI (Java), fhirpath.js and more. Use it for invariants and search parameters, and to see where engines disagree.

×When it breaks

  • A string comes out empty: + gives { } as soon as one side is empty, so a name without given loses its family too. & reads empty as '': family & ', ' & given.first().
  • A number is silently missing: toInteger(), toDecimal() and toDate() give { } for a string they can't convert, and so does division by zero. Check first with convertsToInteger() and friends.
  • exists() is true, but there's no value: a primitive that carries only an extension is still an element (see Extensions). Use hasValue() when the rule needs the value itself.
  • A parse error on text.div: div is a keyword (integer division), so the narrative's div element needs backticks: text.`div`.

!Rules of thumb

  • Read every result as a collection: zero, one or many items.
  • Test with exists(), empty() and count(); never let { } stand in for false.
  • Ask lists with where(), exists(...) or in, not =; compare codes with ~ or by system and code.
  • Narrow to one item before a string function, +, < or single().
  • Try every invariant and search expression on more than one engine before you ship it.

Profiles: what a resource must look like here

How a profile narrows a base resource for one use, how slicing sorts a list, and why meta.profile proves nothing.

Base resource: what is allowed anywhere

Wide on purpose: almost everything optional, several types allowed, loose bindings. It has to fit every country and every use.

Profile: what is required here

A StructureDefinition that narrows the base for one use. R4: "Profiles cannot break the rules established in the base specification", so data valid against a profile is valid against the base.

1What a profile can change

Cardinality0..* to 1..1, or 0 to rule it out
Types, targetsFewer; e.g. only a CH Core Patient
ValuesA fixed value or a pattern
BindingsA stricter ValueSet
InvariantsFHIRPath rules, error or warning
SlicingRules per kind of list entry (2)
ExtensionsWhich are allowed, where, how many
mustSupportElements to "support" (3)

What it can't do: add elements (only extensions add data), widen what the base or a parent profile allows, or give an element a default value or a new meaning.

2Slicing: rules per kind of entry

A repeating element can be cut into slices, each with its own rules. CH Core Practitioner slices identifier:

  • GLN, 0..1: system fixed to urn:oid:2.51.1.3.
  • ZSR, 0..*: system fixed to the ZSR OID; two invariants check the value: one letter and six digits, and a check digit (both warnings).
  • The discriminator (here the value) tells the validator which slice an entry belongs to.
  • The slicing is open, so other identifiers, such as a personnel number, are still allowed. Closed slicing would reject them.
"identifier": [
  { "system": "urn:oid:2.51.1.3",
    "value": "7601000000019" },
  { "system":
      "urn:oid:2.16.756.5.30.1.123.100.2.1.1",
    "value": "D123456" },
  { "system":
      "https://example.org/sid/staff-nr",
    "value": "123456" }
]

GLN slice, ZSR slice, and a third identifier no slice claims. Values made up; both pass their check digits.

3mustSupport: defined by each IG

  • R4: "The meaning of 'support' is not defined by the base FHIR specification." The profile or its IG has to say what it means for senders and receivers.
  • A derived profile can turn mustSupport on, never off.
  • Profiles vary a lot: CH Core Practitioner flags no element at all.

4meta.profile is a claim

  • R4: "An assertion that the content conforms", and "a resource may falsely claim to conform to a profile".
  • Servers "MAY elect to remove invalid claims"; nothing makes them validate.
  • A resource can conform to several profiles at once, and to profiles it doesn't name.
  • Only a validator with the right packages loaded proves it: the HL7 validator CLI, or a server that validates on write.

5Where profiles live

Each profile has a canonical URL, such as http://fhir.ch/ig/ch-core/StructureDefinition/ch-core-practitioner, and a version; a canonical reference can pin one with |, as in <url>|<version>. An IG ships its profiles, extensions and terminology as a package, such as ch.fhir.ig.ch-core#6.0.0: validators and servers load packages, not web pages. Most IGs are written in FHIR Shorthand (FSH, an HL7 standard), compiled by SUSHI and published with the IG Publisher.

×When it breaks

  • Valid, but the ZSR checks never ran: a typo in system means the entry matches no slice, and open slicing accepts it as just another identifier. Test with a wrong ZSR: no ZSR warning means it missed its slice.
  • Error on a Coding with the right code: the profile uses fixed[x], which must match exactly: what it leaves out must be missing too, so an added display fails. pattern[x] only needs its own values.
  • Valid, but a mustSupport element is missing: mustSupport is "distinct from cardinality", so a 0..1 element can still be absent. Handle that, or make it 1..1 in your own profile.
  • No instance validates against your profile: one of its rules contradicts a parent profile's, and then "there is no set of instances that can be valid". Keep a valid example and validate it in CI.

!Rules of thumb

  • Derive from the national profile where one exists (CH Core), not from the base resource.
  • Check data with a validator; never trust meta.profile.
  • Pin the package version you validate against: a stricter new version can turn stored data invalid.
  • Before building against an IG, read what its mustSupport means and which invariants are errors rather than warnings.

Extensions: before you reach for one

What an extension is, what it costs everyone who reads the data, and what to check before defining your own.

extension: extra data

Adds something the base resource has no element for. A consumer that doesn't know it can skip it and still read the rest correctly.

modifierExtension: changes the meaning

Changes how the element around it must be read. R4: implementations "SHALL ensure that they do not process data containing unrecognized modifier extensions". Rarely the right tool.

1Anatomy

  • An extension array can sit on any element. Each entry has a url and exactly one value[x] (valueCoding, valueReference, valueAddress, ...), or nested extensions for a complex one, never both.
  • The url is not a page for people: it is the canonical URL of the StructureDefinition that defines the extension, which says where it may sit (its context), its value type, its cardinality and any ValueSet binding.
  • Primitives can carry extensions too. In JSON they go in a sibling property with an underscore: "_birthDate": { "extension": [ ... ] }.
"extension": [
  { "url": "http://hl7.org/fhir/StructureDefinition/patient-birthPlace",
    "valueAddress": { "city": "Paris", "country": "Frankreich" } },
  { "url": "http://fhir.ch/ig/ch-core/StructureDefinition/ch-core-patient-ech-11-placeoforigin",
    "valueAddress": { "city": "Köniz", "state": "BE" } }
]

From CH Core's example patient Franz Muster, shortened. It reuses the core extension for the birthplace and adds its own only for the place of origin (Heimatort), which core FHIR has no element for.

2What every extension costs

  • A consumer that doesn't know the definition sees nothing: generic viewers, other teams' apps, analytics, the next vendor.
  • The validator can only check it against the published definition, usually from a package.
  • The server can't search on it until someone adds a SearchParameter for it.
  • Its url is stored in every resource that uses it. Changing it means migrating data, so it belongs in a namespace you own for good.
  • An extension that repeats a native element gives two sources of truth, and they drift apart.

R4 says "there can be no stigma associated with the use of extensions". The question is not whether they are allowed, but whether this one earns its cost.

3Before you define one

  1. Read the whole resource: backbone elements, every reference target, the status and type codes. Most "missing" fields are there under another name.
  2. Is it a resource, not a field? A room is a Location, a person a Practitioner: point at it with a Reference, not a name or an id in a string.
  3. Look for an existing one: the R4 core registry, HL7's extensions pack (hl7.fhir.uv.extensions.r4), CH Core, then other IGs.
  4. Only then define your own: a narrow context; a Coding or CodeableConcept bound to a ValueSet, not a bare code or string; published in a package, under your own namespace.

×When it breaks

  • Error on the url: it must be the canonical URL of the extension's StructureDefinition, not a URN such as an OID or a UUID. Only the parts inside a complex extension may use a relative url.
  • Required, but unknown: unless the resource or a profile makes the value itself mandatory, send the element with only a data-absent-reason extension: "_birthDate": { "extension": [ ... ] }. Never invent a value.
  • 422 for a modifierExtension: a server that doesn't know it may reject the resource; R4 names 422 for this. Agree on it with every receiver first, or use a plain extension if ignoring it is safe.
  • 200, but your extension is gone: a system that changes an element "SHOULD remove any extensions that it does not understand" from it and below. Every system that edits the data has to know yours.
  • A search on an extension returns too much: without a SearchParameter for it, the server ignores the parameter and answers 200 with everything the rest matches. Check the self link (see Search).

!Warning signs in a model review

  • A status extension next to the resource's own status: which one wins?
  • A name in a string where a Reference fits, or another resource's id kept in a string or code.
  • A code value with no ValueSet: nobody can tell which codes are valid.
  • The same extension on many resource types to tie them together: look for a native reference or a resource that groups them first.
  • Many extensions on one resource: the model may be fighting the resource; check whether another resource fits better.

Validation and tooling: proving a resource conforms

A profile says what a resource must look like; a validator checks it. The validator, its packages, its terminology server and their versions decide the answer, so pin them all.

The HL7 validator CLI

One Java jar, the reference for what "valid" means: the base spec, every meta.profile and any profile you name, from the packages you load. It exits with 1 on errors, so it works as a CI gate.

Same resource, different verdict

Another package version, no terminology server, a profile that never got loaded: each one changes the result, often into a quiet "Success".

1What a validator checks

StructureEverything is in the spec, "and nothing extra is present".
CardinalityMin and max of every element.
Value domainsValues fit their types: dates, decimals, ids, ...
BindingsCodes and displays are valid for their value sets.
InvariantsThe FHIRPath rules (see FHIRPath).
ProfilesEvery rule of every profile it checks against.
QuestionnairesA QuestionnaireResponse fits its Questionnaire.

People and organisations: who is who

Nine resources for the people, places, teams and services around care. The traps: the person in one resource and their job in another, a ward that is both an Organization and a Location, and teams that could be three different things.

Practitioner is the person, PractitionerRole the job

A Practitioner has no organisation and no role. As what, for whom, where and when someone works sits in a PractitionerRole: one for each combination that differs.

Organization is conceptual, Location physical

The cardiology department and its ward are Organizations; the ward's rooms and beds are Locations. "Locations are always used for recording where a service occurs".

1Who's who

PatientThe subject of care. "generally created and maintained by each organization providing care": one record per organisation.
RelatedPersonInvolved in a patient's care "but who is not the target of healthcare, nor has a formal responsibility": relatives, neighbours, a guardian.
PractitionerAnyone with a formal responsibility in care, "receptionists handling patient registration" and "IT personnel merging or unmerging patient records" included. Not for informal carers: "SHALL NOT be used" for them.
PractitionerRole"A specific set of Roles/Locations/specialties/services that a practitioner may perform at an organization for a period of time."
OrganizationA "grouping of people or organizations formed for the purpose of achieving some form of collective action": hospitals, departments, wards, insurers, practices.
LocationA physical place, "from small freezers to full hospital buildings or parking garages". Not a body site: the playground where the leg broke, not the leg.
HealthcareServiceA service an organisation offers at a location, possibly virtual. Not IT: "do not represent Computer related Services (not SOA)".
CareTeamThe people and organisations who plan to coordinate care for one patient or a group; it may have no subject at all, "such as a code blue team".
GroupA collection "discussed or acted upon collectively but which are not expected to act collectively": a cohort, a patient list for analysis.

2Practitioner and PractitionerRole

  • Practitioner holds what stays the same in every job: identifiers (GLN and ZSR in CH Core, see Profiles), name, gender, birth date, languages, and telecom and address "that apply to all roles" or are "typically home address".
  • qualification: degrees and licences, acquired "independent of any organization or role". They don't allow anyone to work anywhere.
  • The organisation in a role "need not necessarily be the (direct) employer".
  • PractitionerRole: practitioner, organization, code, specialty, location, healthcareService, period, telecom, availableTime. Nothing is required.
  • No address: "the location that is defined here contains the address".
  • Where availability or telecom differ between locations or services, "a seperate PractitionerRole instance should be created".
  • CH Core binds code and specialty to CH Term (preferred); its example: SNOMED CT 309343006 Physician, specialty 1040 General medical practitioner.

Where a reference accepts both, pointing to the PractitionerRole says who acted, as what and for whom; a Practitioner says only who.

3Organization and Location: two hierarchies

  • Organization.partOf builds "a strict Hierarchy": hospital, department, ward. In the Location hierarchy, "Wards/departments are not part of this structure - these would form part of the Organizational Hierarchy."
  • type codes from organization-type: prov, dept ("A department or ward within a hospital"), team, ins, pay, govt, ... Prefer child organisations to piling up types; a ward's local number is an identifier, not a code.
  • org-1: a name or an identifier. org-2 and org-3: no home address or telecom.
  • active is a modifier, and not for a temporary closure: suspend the Locations instead.
  • telecom is the public point of contact; contact a person or party for a purpose, such as billing.
  • Swiss identifiers: GLN, UIDB (CHE plus 9 digits, no separators), BER, ZSR (see CH Core).
  • Location.partOf: building, wing, level, room, bed. physicalType: si, bu, wi, wa, lvl, ro, bd, ...; a bed is "the space it may occupy", not the trolley.
  • managingOrganization joins the hierarchies, at any level, not only the top.
  • status (a modifier): active, suspended ("temporarily closed"), inactive. operationalStatus, a Coding for beds from v2 table 0116: O occupied, U unoccupied, H housekeeping, K contaminated, I isolated, C closed.
  • mode: instance (Operating Theatre 1A) or kind (any operating theatre). Arrived "by ambulance", but which one is unknown: an instance without an identifier, not a kind.
  • One address at most; position in WGS84.

5Patient: records, duplicates, contacts

  • One managingOrganization per record: "Other organizations will have their own Patient record, and may use the Link property to join the records together".
  • active is a modifier: false for a duplicate or a record created in error. Deceased patients "may be active for some time after death".
  • deceased[x] is a modifier too; "Most systems will interpret the absence of a value as a sign of the person being alive."
  • multipleBirth as an integer is the birth order: "The middle birth in triplets would be valueInteger=2".
  • generalPractitioner: an Organization, Practitioner or PractitionerRole, "not to be used to record Care Teams".
  • "Around 2% of registrations are in error, mostly duplicate records." The duplicate gets a link of type replaced-by to the record to use; the survivor may link back with replaces. Also refer and seealso.
  • Follow the chain: the target "may in its turn" be replaced. Links needn't be mutual, and R4 "does not specify merge functionality".

6Teams, groups and services

  • CareTeam: participants with roles; a member can be a Practitioner, PractitionerRole, RelatedPerson, Patient, Organization or another CareTeam. onBehalfOf only for a Practitioner member (ctm-1). status is a modifier.
  • Organization of type team: a standing team in the org chart; Organization.type counts "clinical teams".
  • Group: type (person, practitioner, device, ...) and actual are required. Real members only if actual is true (grp-1); otherwise characteristics define it. Members can't be RelatedPersons or Organizations.
  • HealthcareService: providedBy (best the Location's managing organisation), location, type, specialty, availableTime, appointmentRequired. Holidays and maintenance go in notAvailable, not active.

  • 200, but half the history: after a replaced-by link, servers needn't move data off the duplicate. Find linked records with Patient?link=Patient/123 and search all their ids.

  • Departments and wards are Organizations; rooms and beds are Locations; managingOrganization joins them.
  • Anyone you need to reference who isn't staff is a RelatedPerson; Patient.contact can't be referenced.
  • Skip inactive Patients and follow replaced-by links to the end; R4 defines no merge.
  • Before choosing a team resource, check what the references you need will accept.

Clinical data: what happened, and does it still count?

Encounter, Condition, Observation, Procedure and AllergyIntolerance carry most clinical facts. Each has a status that can turn a record into its opposite: refuted, not done, entered in error. Read it before anything else.

Status first, then the data

Modifier elements such as status and verificationStatus "cannot be safely ignored". A refuted Condition is a diagnosis ruled out; an Observation in entered-in-error never happened.

Search doesn't filter for you

R4 has no rule that servers hide entered-in-error or refuted records from a search. Filter by status yourself, and mind the records that have none.

1Statuses that change meaning

Encounter statuscancelled ("ended before it has begun"), entered-in-error
Condition, AllergyIntoleranceclinicalStatus: inactive, resolved, remission. verificationStatus: refuted (ruled out), entered-in-error, and unconfirmed, provisional, differential
Observation statuspreliminary, amended and corrected, cancelled ("not started or not completed"), entered-in-error
Procedure statusnot-done (nothing beyond preparation), stopped (part of it happened), entered-in-error
  • A modifier is an element that "cannot be safely ignored"; systems "SHALL understand the impact" and "SHOULD always check the value". Yet "Even something as critical as Observation.code is not a modifier element."
  • entered-in-error: "created accidentally and should be ignored". For Observation and Procedure, "it is possible that real-world decisions were based on it"; if something really happened, the status is cancelled or stopped instead.
  • An old version that was wrong: point a Provenance at that version (see Audit, provenance, consent).
GET [base]/Condition?patient=123
    &clinical-status=active,recurrence,relapse
GET [base]/Condition?patient=123
    &clinical-status:missing=true
GET [base]/Observation?patient=123
    &status:not=entered-in-error

One request per line, wrapped here. R4: "Resources missing a clinicalStatus will not be returned. This is probably unsafe", so ask a second time with :missing=true.

2Encounter

  • status: planned, arrived, triaged, in-progress, onleave, finished, cancelled, entered-in-error, unknown. The only modifier in Encounter.
  • Admitted? "There is no direct indication purely by the status field"; at the least, a patient "IS admitted when the status is in-progress".
  • class is one Coding, 1..1, not a CodeableConcept: v3 ActCode AMB, EMER, IMP, SS, HH, VR, ...
  • partOf nests encounters, such as a ward stay inside a hospital stay. hospitalization covers the same period as its encounter; a different period means another encounter, partOf this one.
  • location: each with status (planned, active, reserved, completed) and period. The spec's own text mentions a status "present", which isn't a code.
  • diagnosis: a Condition or Procedure, a use (AD admission, DD discharge, CC chief complaint, CM comorbidity, billing, ...) and a rank per use. The Condition page calls it "Encounter.diagnosis.role"; the element is use.
  • serviceProvider: the Organization primarily responsible. period.end stays empty while it isn't known.
  • CH Core adds the BFS medical statistics extensions on hospitalization (see CH Core).

Medications: ordered, handed out, given, taken

Four resources for four different facts: someone asked for a drug, a pharmacy handed it out, a nurse gave it, the patient says they take it. Plus Dosage, the most used and most misread data type, and CH EMED for Switzerland.

One resource per fact

MedicationRequest is the order, MedicationDispense the supply, MedicationAdministration one dose given, MedicationStatement what someone reports the patient takes.

A statement is not part of the chain

MedicationStatement "is not a part of the prescribe->dispense->administer sequence, but is a report". Never conclude from one that a dose was given.

1Four resources

MedicationRequest"an instruction for the administration of medication": a prescription or an order, one medication per request. status: draft, active, on-hold, completed, stopped, cancelled, entered-in-error, unknown.
MedicationDispense"The provision of a supply of a medication", usually against a prescription. status: preparation, in-progress, on-hold, completed, stopped, cancelled, declined, entered-in-error, unknown.
MedicationAdministration"a patient actually consuming a medicine, or ... administered": one event, with a required effective[x]. Its dosage is its own element with a dose or a rate (mad-1), not the Dosage type. status includes not-done.
MedicationStatementThe patient "may be taking a medication now, has taken ... in the past, or will be taking" it. "only representative at the point when it was asserted". status includes intended and not-taken (R4 dropped taken).
  • The first three each record "an individual order, an individual provisioning of medication or an individual dosing"; a statement "is a broader assertion covering a wider timespan".
  • The current medication list is a curated List of these, not a search: requests, dispenses and statements overlap and contradict each other.
  • medication[x] is a CodeableConcept or a Reference to Medication. "If only a code is specified, then it needs to be a code for a specific product."
  • Form, lot number, or a compounded drug: "you must reference the Medication resource", often contained (see Data types).

  • Prefer structured timing with UCUM units; BID means the institution's times, timeOfDay means yours.

Orders and tasks: asking another system to act

Requests ask, events record, and Task tracks the work in between. How intent and status separate the authority from the execution, what a ServiceRequest carries, and the ways a placer and a filler can talk.

A request's status is the authority, not the work

"The status of a request only reflects the status of the "authorization/intention"". Whether the lab has started shows in a Task, or in the events based on the request.

Status names drift

The Request pattern says suspended and cancelled; ServiceRequest says on-hold and revoked. Read each resource's own code system, not the pattern.

1Requests, events, definitions

Request"ask for or express a desire/intention for something to be done": ServiceRequest, MedicationRequest, CarePlan, CommunicationRequest, DeviceRequest, ...
Event"something has been done": Procedure, Observation, DiagnosticReport, Encounter, MedicationAdministration, Communication, ...
DefinitionWhat "can potentially happen", independent of patient and time: ActivityDefinition, PlanDefinition, Questionnaire, ...

Scheduling: finding a free slot and booking it

Schedule, Slot, Appointment and AppointmentResponse, built on iCal conventions: who has time, which slots are free, the booking, and each participant's answer.

Slots are free or busy time, nothing more

A Schedule holds an actor's bookable time, its Slots say free or busy. They "do not provide any information about appointments".

Free doesn't mean bookable

"Just because a time is indicated as available doesn't guarantee that an appointment can be made." Book, then read the status you get back.

1Four resources

Schedule"a container for time-slots that can be booked". actor 1..*: Patient, Practitioner, PractitionerRole, RelatedPerson, Device, HealthcareService or Location; planningHorizon. It "does not provide any information about actual appointments".
Slotschedule, status (free, busy, busy-unavailable, busy-tentative, entered-in-error), start and end, all required; overbooked. Separate resources "Due to the dynamic nature of slots".
Appointment"a planned meeting that may be in the future or past", "only ... a single meeting": a series is several Appointments. Participants 1..*, the slots it fills, basedOn a ServiceRequest. Administrative only; "the Encounter is expected to have clinical implications".
AppointmentResponse"A reply to an appointment request": appointment, actor, participantStatus, and a proposed new start and end.

A slot "can have more than one appointment allocated to it"; whether to overbook is up to "the server business rules". The spec's example: 8 one-hour appointments on 5 days are one Schedule and "40 (5x8) Slot resources".

Documents: a signed-off record in one Bundle

A FHIR document is a Composition plus everything it points to, frozen in a Bundle of type document. PDFs, scans and CDA files go another way: a Binary for the bytes, a DocumentReference to find them. Then CH Core's document profiles.

A document is frozen

"Once assembled into a bundle, the document is immutable": its content "can never be changed, and the document id can never be reused". A correction is a new document.

A Composition alone is not a document

"a Composition alone does not constitute a document". It has to be the first entry of a document Bundle that also carries everything it references.

1Three ways to carry a document

FHIR documentA Bundle with type document, Composition first. "for documents that are authored and assembled in FHIR": narrative for people, structured resources for software.
DocumentReference"for general references to pre-existing documents": PDF, CDA, scans, images. Metadata to find and manage the document; the bytes live in a Binary, on another server, or inline. It can also point at a FHIR document stored elsewhere.
Binary"the data of a single raw artifact" plus its contentType. No context and no search: usually a DocumentReference points at it.

SMART on FHIR: OAuth 2.0 for health data

FHIR defines no security of its own. SMART App Launch 2.2.0 profiles OAuth 2.0 for it: how an app finds the endpoints, gets launched, asks for scopes and calls the API with a token, and how a backend service does the same without a user.

FHIR assumes security, SMART supplies it

FHIR "is not a security protocol, nor does it define any security related functionality". R4 recommends OAuth, and SMART as "a recommended method for using OAuth".

You get what's granted, not what you asked for

"the scopes ultimately granted by the authorization server may differ from the scopes requested by the client!" Read scope in the token response.

×When it breaks

  • No redirect, just an error page: the redirect_uri doesn't match one registered for the client, or the client_id is unknown. The server won't send the browser back; fix the URI or the registration.
  • error instead of code on the redirect: access_denied means the user or the server said no; invalid_scope, a scope it doesn't know or can't parse. Check state here too, then tell the user.
  • 400 invalid_grant on the code exchange: the code was used already or has expired (often within a minute), redirect_uri differs from the authorize request, or the code_verifier doesn't match. Start again at authorize.
  • 400 invalid_grant on a refresh: the refresh token expired or was revoked, or it's an old one the server dropped when it issued a new one. Always keep the newest; if it still fails, send the user through authorize again.
  • 400 or 401 invalid_client with a signed JWT: aud isn't the token URL, exp is more than five minutes ahead, the jti was used before, or no registered key matches its kid. Fix it and sign a fresh one.
  • 200, but a scope is missing from scope: permissions out of order or undefined, such as .dus, may be ignored, replaced with defaults or rejected. Keep the cruds order: .uds.

  • Read [base]/.well-known/smart-configuration; never hard-code endpoints.
  • Every authorize request: PKCE with S256, a fresh state, aud set to the FHIR base.
  • Ask for the narrowest scopes, then read the scope you were granted.
  • The token goes in the Authorization header: never in a URL or a clear-text cookie.
  • Backend services: sign a JWT, use the token for five minutes, ask again.
  • 401: get a new token. 403: this token can't do that. An empty 200 may be policy, not absence.

Audit, provenance, consent: who did what, and who may

Four things that are easy to mix up: AuditEvent logs access, Provenance records where data came from, security labels tag sensitive data, Consent records a patient's choices. FHIR stores all four; enforcing them is up to the server.

Audit for reads, provenance for writes

Provenance "can record details for Create, Update, and Delete"; "Generally, Read operations would be recorded using AuditEvent". AuditEvent "is created as events occur".

Recorded isn't enforced

"The enforcement of the Privacy Consent Directive is not included". Labels only work where every partner has agreed to honour them. Your access control does the work.

×When it breaks

  • 400 on "outcome": 0: outcome is a code, and codes are JSON strings: "0", "4", "8", "12". The same trap waits in the network type: "2".
  • Only successes in the log: access control decisions are security events too, so record refused and failed requests: 4 is "often equivalent to an HTTP 400 response", 8 to a 500.
  • 200 on a PUT, but the label you dropped is still there: on update, servers generally merge existing and new security labels. Remove one with $meta-delete, matched by system and code (see Operations and PATCH).
  • No meta.security, so nothing sensitive? Without a confidentiality code, confidentiality "may be implied by its definition and content"; a report with an HIV test is "always highly confidential". Judge by content.

  • Reads go to AuditEvent, writes get a Provenance; keep the audit log append-only.
  • Put the patient in an AuditEvent entity, and take the shapes from IHE BALP.
  • Send a Provenance with its target in one transaction.
  • A Consent records a decision; your access control enforces it. Set its patient even though R4's invariants won't complain.
  • Read meta.security on everything you receive, and keep the labels when you pass data on.
  • In the EPD, confidentiality is SNOMED CT, not v3.

The EPD: Switzerland's patient record over FHIR

The EPD (elektronisches Patientendossier, "EPR" in the specs) links certified communities that hold documents about a patient. Its FHIR API is a set of IHE profiles with Swiss rules on top, written down in CH EPR FHIR 5.0.0 and made binding by ordinance. This is what a developer meets: the national patient number, the PIXm and PDQm lookups, the MHD document transactions and their metadata.

IHE profiles you learn once

MHD for documents, PIXm and PDQm for patients, IUA for tokens. The Swiss extensions "shall be used in conjunction with" the IHE definitions: read the IHE transaction first, then the CH page for what it adds or forbids.

No Patient to point at

"No addressable patient resources": there is no national master patient, so every patient reference is the EPR-SPID as an identifier. And "Systems are not allowed to store the EPR-SPID".

1What the EPD is

WhatA "virtuelles Dossier" over "dezentral abgelegte behandlungsrelevante Daten" (EPDG Art. 2): the documents stay with the communities, which are networked with each other and with a few central federal components. Residents have been able to open one since 2020.
CommunitiesA Gemeinschaft is an "organisatorische Einheit von Gesundheitsfachpersonen und deren Einrichtungen". A Stammgemeinschaft, chosen by the patient, is where the EPD is opened and managed: consents, access rights, patients' own data. Access logs are kept for ten years (EPDG Art. 10).
Who must joinInpatient institutions that bill compulsory health insurance (OKP): hospitals, rehabilitation and psychiatric clinics, nursing homes, birth centres; since 2022-01-01 also newly admitted doctors (KVG Art. 39 and 37). Voluntary for patients and everyone else.
ConsentOpening one needs "die ausdrückliche Einwilligung" of the patient, who can withdraw it "jederzeit ohne Angabe von Gründen" (EPDG Art. 3).
ConfidentialityThree levels: normal, restricted (eingeschränkt), secret (geheim), normal by default. Professionals can be granted normal, or normal and restricted; secret is for the patient alone. Emergency access reaches normal data, and the patient is told (EPDV Art. 1 and 2).
RetentionWhat professionals enter is "nach 20 Jahren vernichtet"; the patient can ask for exceptions, or for deletion sooner (EPDV Art. 10).
What's nextThe EGDG (business 25.082) replaces the EPDG: the EPD becomes the E-GD, with federal central infrastructure, automatic opening with opt-out, and every provider billing OKP, UV, IV or MV obliged to join. The Nationalrat passed it on 2026-09-14; the Ständerat is next. It can start "frühestens 2030"; until then the EPDG applies.

2Who is the patient: three numbers

Local idYour system's patient number, type MR, under your own OID, such as urn:oid:2.999.1.2.3.4|8734.
MPI-PIDThe community's master patient index id. Each community has its own assigning authority; there is no national one.
EPR-SPIDThe national number, system urn:oid:2.16.756.5.30.1.127.3.10.3. 18 digits: 76 (country), 13376 (the BAG), 1 (the EPD), nine random digits, a check digit. It "darf keinerlei Rückschlüsse auf die Patientin oder den Patienten zulassen". The ZAS issues it at a Stammgemeinschaft's request.
AHVN13Communities may use it for two things only: asking the ZAS for the EPR-SPID, and assigning it correctly (EPDG Art. 5). "Aus der EPD-SPID allein kann die AVHN13 nicht abgeleitet werden" (sic).
  • "Systems are not allowed to store the EPR-SPID, and need to feed their local identifier (localID) and EPR-SPID to the community to resolve the localID to the EPR-SPID later on." So: feed both to the community's PIXm (below), keep only your own number, and look the EPR-SPID up when you need it.
  • Typed in by hand, it may only be accepted after checking the check digit (EPDV Art. 7).
  • Check digit: weights 3, 1, 3, 1 ... from the right over the first 17 digits, then whatever brings the sum up to the next multiple of ten. 76133761041135365 sums to 120, so the IG's example 761337610411353650 ends in 0.
  • CH Core's EPR-SPID datatype only warns on a bad format or check digit; its Patient EPR profile forbids the EPR-SPID and the AHVN13 in EPD documents (see CH Core).

11On every call

  • TLS always; "Transactions across communities SHALL use mTLS."
  • Either an IUA access token in Authorization: Bearer (ITI-72), or mTLS plus a XUA token, "conveyed as defined in" ITI-72. Signed JWTs only: "The JWE alternative SHALL not be used", and the "Token Introspection Option SHALL NOT be used".
  • Where the EPR-SPID is in both the token and the body, "the Resource Servers SHALL verify that both are the same".
  • Responders ask CH:ADR for an authorization decision; every actor writes CH AuditEvents through RESTful ATNA, and patients read them with CH:ATC.
  • "The actors SHALL support the traceparent header handling": W3C Trace Context, one id for one request across communities.
  • The patient's access rights are CH:PPQm policies, managed through the Stammgemeinschaft. When they say no, IHE's guidance allows a 200 with less in it, a 403 or a 404: don't read an empty result as "nothing there".

×When it breaks

  • ITI-65 fails with XDSUnknownPatientId: the community doesn't know that EPR-SPID. Get it from ITI-83 just before the call, never from a stored copy; a 404 there means your patient was never fed (ITI-104).
  • XDSDuplicateUniqueIdInRegistry or XDSNonIdenticalHash: the masterIdentifier, or the SubmissionSet's uniqueId, is already registered. A corrected or replacing document is a new version: give it a new uniqueId.
  • 200 with PartialReplaceContentNotProcessed: the new document is in, but the recipient didn't process replaces. Don't take the old one as superseded: check its status with ITI-67.
  • XDSMetadataIdentifierError or XDSPatientIDReconciliationError on CH:MHD-1: the PUT changed an identifier or the patient, and nothing was saved. Start again from the DocumentReference as you read it.

!Rules of thumb

  • Learn the IHE transaction, then read the CH page on top; build against the versions EPDV-EDI Annex 5 names.
  • Never store the EPR-SPID: feed it with ITI-104, keep your own number, ask ITI-83 when you need it.
  • Refer to the patient by EPR-SPID identifier, always with the system; there is no Patient URL to use.
  • A 403 from $ihe-pix means a wrong targetSystem; an empty $match may mean "too many".
  • Follow attachment.url as returned, and check search results for OperationOutcome warnings.
  • Documents don't change: replace them, and change only the metadata Annex 5.1 allows.

Normative content doesn't break

Once normative, "the names, path and meaning of previously existing data elements will not be changed". In R4 that covers Patient, Observation, Bundle, the REST API, search and the data types.

Trial use can change anything

For trial-use content "There are no rules for maintaining any sort of compatibility between versions". That's most R4 resources: Encounter, MedicationRequest, Appointment, Task and the rest.

2Normative and trial use: what is promised

Normative in R4Resources Resource, DomainResource, Binary, Bundle, CapabilityStatement, CodeSystem, Observation, OperationDefinition, OperationOutcome, Parameters, Patient, StructureDefinition, ValueSet; the data types, references, JSON and XML, the RESTful API, search, operations, terminologies, FHIRPath. Each page shows its "Standards Status".
Mixed"Some normative resources contain elements labeled as 'trial-use'", such as Bundle.signature.
ElementsNew optional elements may come, never as modifiers; existing names, paths and meanings stay.
Cardinality"Minimum element cardinalities will not be changed." A maximum may go from 1 to * only when the extra repetitions "can be safely ignored", and "this may change the path to the element" in JSON: an object becomes an array.
TypesNot removed or changed, "except for the special case that string may be changed to markdown".
Bindings"Required bindings will remain required and will continue to point to the same value set."
  • The aim is forward compatibility: old conformant applications stay conformant. Backward compatibility "is not guaranteed by FHIR", and even forward "doesn't guarantee that all old systems will interoperate with future systems".
  • It works: Patient's whole R4 to R5 diff is one binding change, on communication.language; Observation mostly gained elements and types, and lost Media as a derivedFrom target only because Media itself is gone.
  • So read tolerantly. Applications SHOULD "Ignore elements that are unexpected (new elements will never be modifier elements)", "Ignore unrecognized codes in required and extensible bindings unless the element they appear on is a modifier", "Ignore unrecognized search criteria".
  • Trial-use pages show a maturity level, FMM 0 to 5, which "can be used by implementers to judge how advanced - and therefore stable - an artifact is". FMM 5 means two trial-use publications and five production systems in more than one country.

  "period": { "start": "2026-10-28T09:00:00+01:00" },
  "reasonCode": [ { "text": "Appendicitis" } ],

5Which version is this?

GET [base]/metadata
Accept: application/fhir+json; fhirVersion=4.0

200 OK
{ "resourceType": "CapabilityStatement", "fhirVersion": "4.0.1", ... }

GET [base]/$versions

200 OK
{ "resourceType": "Parameters",
  "parameter": [ { "name": "version", "valueCode": "4.0" },
                 { "name": "version", "valueCode": "5.0" },
                 { "name": "default", "valueCode": "4.0" } ] }
  • Three places say it: CapabilityStatement.fhirVersion; the fhirVersion MIME parameter, major and minor only (4.0, 4.3, 5.0), on Accept, Content-Type or both; a version-specific profile in meta.profile.
  • "the applicable FHIR version applies to the entire interaction, not just the resources". R4: "It is an error for a client to attempt to use two different versions in the same interaction." R5 allows a different Accept and Content-Type version only for "an operation that is specifically defined to perform version conversion".
  • Stored files: keep the version with them. When several statements exist, "the version statements must all agree with each other, or it is an error".
  • "The most common strategy" is one endpoint per version, such as /fhir/r4 and /fhir/r5. One endpoint can serve several if the client sends the parameter; when metadata comes back with another fhirVersion, the server ignored it. "The client must include the fhirVersion parameter on all following interactions."
  • HAPI: one version per server and per FhirContext, so R4 plus R5 means two of each; hapi.fhir.org serves /baseR4, /baseR4B and /baseR5 side by side (see Validation and tooling).
  • $versions lists the major.minor versions and the default. R4's own example sends valueString, R5's valueCode; the type is code in both, so accept both.
  • The validator defaults to R5: pass -version 4.0.1 (see Validation and tooling).

6Migrating

  • What changed: each R5 resource page has "Changes from both R4 and R4B"; R5's diff page is "an automatically generated list of all the structural differences".
  • Maps: R5 ships R4 <-> R5 transforms in the FHIR Mapping Language, "not authoritative"; newer ones live in the FHIR Cross-Version Mapping Pack, still a draft.
  • $convert changes the format (XML and JSON), not the version.
  • Code: HL7's Java core has VersionConvertorFactory_40_50.convertResource(...), R4 to R5 and back; HAPI wraps it in hapi-fhir-converter, "an experimental feature so use it with caution!". The validator CLI converts between versions too.
  • Going back from R5 to R4, elements with no R4 home travel as cross-version extensions (below) or get lost: check what your converter does.
  • Convert at the edge: keep your store in one version and map at the interface that needs another.

7R5 data in R4: cross-version extensions

http://hl7.org/fhir/[version]/StructureDefinition/extension-[Path]

{ "resourceType": "Encounter", "status": "planned",
  "extension": [ {
    "url": "http://hl7.org/fhir/5.0/StructureDefinition/extension-Encounter.plannedStartDate",
    "valueDateTime": "2026-11-03T08:00:00+01:00" } ],
  ... }
  • Every element of every version has an extension URL on that pattern: version 1.0, 3.0, 4.0, 4.3 or 5.0, and the path the element's id in that version.
  • "Implementations should always use the correct element for data when one exists", and "It is always an error to use a cross version extension in the same version".
  • A type new to an existing element goes in the later version's extension, such as extension-Observation.value. "The extension mechanism carries no information about cardinalities"; elements typed as a whole Resource are excluded.
  • The packages: the spec's table names hl7.fhir.extensions.r4, which doesn't exist. Use hl7.fhir.uv.xver-r5.r4 0.1.0 (2026-03-20, "First release for testing", maturity 0): source version first, target second. Its siblings go the other ways (xver-r4.r5 and more). Known limitation: "Not 100% coverage of all elements in all versions".
  • R5-only resources become R4 Basic resources with a profile, such as profile-ActorDefinition.
  • CH Core 7.0.0-ballot depends on hl7.fhir.uv.xver-r5.r4#0.1.0 for R5 Consent elements in R4: decision, grantor, controller, manager, period and more (see CH Core).

The URL, its context and type are as defined in xver-r5.r4 0.1.0; the date is made up.

×When it breaks

  • 400 for R5 data on an R4 server: ignoring unknown elements is only a SHOULD, "many implementers are unwilling", and JSON readers may also refuse them. Carry R5-only data in cross-version extensions.
  • An R5 code on a modifier: Encounter status completed isn't an R4 code, and on a modifier an unknown code counts as an unknown modifier extension: refuse or warn. Send finished; both mean "The Encounter has ended."
  • 200, but the date filter did nothing: date-start and end-date are R5 search parameters; an R4 server doesn't know them, so it ignores them. Use R4's date, or send Prefer: handling=strict to get an error.

!Rules of thumb

  • Name the version everywhere: 4.0.1 in packages and the validator, fhirVersion=4.0 on the wire when a server serves several.
  • Bet on normative content; treat trial-use resources as moving targets.
  • Read tolerantly: ignore unknown elements, codes and search parameters unless they are modifiers.
  • One version per exchange; convert at the edge, not in your store.
  • In R4 code, avoid what R5 removed when you have the choice: DocumentReference rather than Media, List rather than DocumentManifest.
  • R5 data in R4: the xver-r5.r4 extensions, never in R5 itself. Don't build on R6 ballots or CI builds.

When things break: errors, silent failures, retries

Most failures come back as a status code with an OperationOutcome that says what went wrong. The expensive ones come back as 200. This lesson collects both, as the R4 spec defines them, with what to do about each.

Loud failures are easy

A 4xx or 5xx with an OperationOutcome names the problem: how bad (severity), what kind (code) and where (expression).

Quiet failures cost the most

A misspelt search parameter, a batch with failed entries, a conditional create that found a match: all of them answer 200.

1Read the error: status first, then the OperationOutcome

GET [base]/Condition?onset=23%20May%202009

400 Bad Request
Content-Type: application/fhir+json

{ "resourceType": "OperationOutcome",
  "issue": [ {
    "severity": "error",
    "code": "value",
    "diagnostics": "...",
    "expression": [ "http.onset" ] } ] }

The request is R4's own example of a bad date; the response shows the shape only. Message texts differ between servers and versions.

  • "In case of failure, servers SHOULD always return a body that contains an OperationOutcome resource." It "must include at least one issue", and when the status is 300 or more, at least one issue "should have a severity of" error.
  • code (IssueType) is what to branch on; details may add the server's own finer code; diagnostics is for the log. Never parse message text.
  • expression says where: simple FHIRPath into the resource (Patient.identifier[2].value, never .resolve()), or http. plus a parameter or header name for the request: http.code, http."name:exact".

2Status codes per interaction

read200, 404, 410
vread200, 404; 410 for a deleted version
history200; 404 if the server keeps none
create201, 400, 404, 405, 422
update, patch200, 201, 400, 404, 405, 409, 412, 422
delete200, 202, 204, 404, 405, 409, 412
search200; on failure 400, 401, 404
transaction200, 400, 404, 405, 409, 412, 422; 5xx
  • 400 or 422? Failing the constraints in the CapabilityStatement "should be a 400", other business rules a 422. But "there's no expectation that servers will tightly adhere to this differentiation", and they "may also return 5xx errors in these cases without being deemed non-conformant". On a write, treat 400, 422 and 5xx alike: read the OperationOutcome.
  • These are the FHIR-specific codes, "in addition to normal HTTP errors related to security, header and content type negotiation issues". Gateways and proxies add their own.
  • Not supported at all: conditional operations, batch and transaction "SHOULD return an HTTP 400"; no HEAD gives 405 or 501.

3What each code means

400 Bad RequestCan't be parsed or fails basic FHIR rules. On PUT: no id, or one that differs from the URL. Conditional update: the id you sent isn't the one found.
401 UnauthorizedAuthentication missing or failed: get a new token (see SMART on FHIR).
403 ForbiddenThe server knows who you are, and the answer is no.
404 Not FoundNo such resource or type, "not a FHIR end-point" (check the base URL), or a history the server doesn't keep. Also allowed for access denied, so nothing leaks.
405 Method Not AllowedPUT to a new id where the server assigns ids; DELETE refused for the whole type.
406, 415Accept asks for, or Content-Type sends, a format the server doesn't support.
409 ConflictCan't be done to this resource now: a DELETE refused because others reference it, or a lock on the server.
410 GoneDeleted. Search no longer finds it; a PUT to the same id can bring it "back to life".
412 Precondition FailedIf-Match names an old version, or conditional criteria matched more than one resource.
422 Unprocessable EntityBreaks a profile or a business rule.
5xxThe server failed, or, as above, rejected bad input the rough way.

4Silent failures: 200, and still wrong

Unknown search parameterServers "SHOULD ignore unknown or unsupported parameters", so a typo widens the result. Compare the self link with what you sent, or send Prefer: handling=strict (honoured by choice).
Empty search parameter"Empty parameters are not an error - they are just ignored": Patient?identifier= returns every patient.
Unknown code or subjectNot an error: 200 with an empty Bundle, perhaps an OperationOutcome entry with mode outcome.
Access deniedAn empty Bundle is one of R4's ways to say no. Empty doesn't prove there's no data.
Batch200 "regardless of the success of the operations within the Batch": check every response.status.
Conditional createOne match: 200 and nothing created. Tell 200 from 201.
Delete"if the resource does not exist at all", still 200, 202 or 204.
Partial read, full writeA resource read with _summary or _elements "is not suitable for use as a base to update": PUT it back and the rest is gone.
What you didn't modelPUT replaces the whole resource. Read the latest version, change only your part, write it back with If-Match, or extensions from other systems disappear.

5Retry or fix?

Retry with backoff5xx, a few times only, since some servers answer bad input with 5xx too; 409 from a lock; IssueType transient and its children lock-error, no-store, exception, timeout, incomplete, throttled: the client "may be able to resubmit the same content once an underlying issue is resolved". Honour Retry-After.
Re-read, then retry412 on If-Match: read the current version, apply your change again, PUT with the new ETag. R4 expects clients to "handle a 409 or 412 response (usually by trying again)".
Fix the request400, 405, 406, 415, 422; 412 on conditional criteria (make them selective: an identifier with its system); IssueType processing and its children, where "there is no point resubmitting the same content unchanged".
New token401.
Stop and report403, 404, 410: the same request will get the same answer.

A timeout after a POST doesn't tell you whether the resource was created. Retry only writes that are safe to repeat: conditional create with If-None-Exist, PUT to a known id, conditional update on an identifier (see Bundles).

7Transactions: all or nothing

  • Servers "SHALL either accept all actions and return a 200 OK ... or reject all resources and return an HTTP 400 or 500 type response".
  • One entry fails, the transaction fails. So do two entries for the same resource, and a conditional reference with no match or several.
  • After a failure nothing from the Bundle is stored: fix it and send the whole Bundle again.

8Make failures traceable

  • X-Request-Id is "purely to help connect between requests and logs/audit trails". Send your own; if the server assigns another, it returns yours in X-Correlation-Id.
  • Prefer: return=OperationOutcome on a write asks for "hints and warnings about the operation" instead of the resource, so you see what the server noticed even when it succeeded.
  • An interface engine that changes the exchange "SHALL mark the request" with X-Intermediary: look for it when the answer doesn't fit the question.
  • Log the status, the request id and the issue codes and expressions, not patient data: logs are "as sensitive as the resources themselves".

!Rules of thumb

  • Read the status, then the OperationOutcome's code and expression; log diagnostics, never parse it.
  • On a write, handle 400, 422 and 5xx the same way: servers aren't strict about which one they send.
  • Assume a 200 can hide a failure: check every batch entry, the search self link, 200 against 201.
  • Retry only what is transient, and only writes that are safe to repeat.
  • Send X-Request-Id and log it with every failure.
